# Bukan MCPでPDF全体を読む

Bukanは、このPCのGoogle Drive for desktopから見えるPaperpileフォルダを読み取り専用で使います。
同期済みPDFとオンデマンドPDFを、既存の文献IDから開きます。クラウドのDrive APIへのログインは不要です。
PDF取得時にはDriveが実体をダウンロードする場合があるため、ネットワーク接続とDrive側の利用可能状態が必要です。

研究解析では、この全文読解を[網羅的な先行研究解析](exhaustive-review.md)の一工程として使います。
引用・非引用の探索、主張・関係の詳しい検証、残件と再開条件は同手順に従って保存します。

## 準備と起動

Windows用配布物の`install.cmd`はPopplerの`pdfinfo`、`pdftotext`、`pdftoppm`をBukan専用の依存領域へ準備します。通常の[2段階の導入](usage.md)では、Popplerの別途インストールやPATH編集は不要です。

手動構成ではPopplerをPATHに置きます。Windowsで自分で管理する場合の例です。

```powershell
winget install --id oschwartz10612.Poppler --exact
```

手動でPATHを変更した場合はMCPホストとターミナルを再起動します。既に使えるPopplerがあるなら再インストールは不要です。配布物のCLIから文献管理MCPを起動できます。

```powershell
bukan mcp C:/Research/my-workspace
```

`mcp`は標準入力からリクエストを待ちます。`bukan mcp-config C:/Research/my-workspace --format toml`でクライアント用設定を表示できます。
研究エンジンとは別のMCPです。文献検出・PDF取得はBukan、読解結果・知見・改訂の保存は研究エンジンが担当します。

## 文献は保存済みライブラリから探す

全文の取得は次の順で進めます。

1. **Google Drive／Paperpile**：Bukanの読み取り専用索引を題名・著者・年で検索し、保存済みPDFを確認する。
2. **出版社**：ローカルで取得できなかった場合に、出版社の公開本文や利用可能なアクセス経路を確認する。
3. **プレプリント・著者公開版**：arXiv、著者最終稿、機関リポジトリなどで対応論文と版を確認する。
4. **未取得の記録**：どこでも全文を取得できなければ、必要な理由と試した経路を台帳に残す。

ローカル索引にDOIがない場合もあるため、題名と著者でも検索します。ファイル名・年だけで同一版とは判断せず、
`get_paper_document`で実体・ハッシュ・ページ数を確認します。Driveのオンデマンド取得失敗や索引の不調は
未所蔵と区別します。ライブラリに接続できない場合は「ローカル確認不能」と残し、未所蔵と断定しません。
所蔵が後から確認できたら台帳の現在状態を訂正し、過去の外部取得失敗は確認履歴として残します。

## 取得と読解を区別する

1. `search_library`で文献IDを取得する。
2. `get_paper_document(paperId)`でSHA-256と総ページ数を取得する。
3. `read_paper_pages(paperId, sha256, startPage=1, pageCount=3)`で本文を取得して読む。
4. `nextPage`が返る間は、そのページから読み進める。
5. `read_paper_page_image(paperId, sha256, page)`で図表・数式を確認する。
6. 全ページの確認状況と、根拠付きの文献ノートを研究エンジンへ保存する。

複数の文献は[文献別のサブエージェント](parallel-review.md)へ割り当てます。同じPDF版について取得済みの本文・ページ画像を共有し、
文献ごとの作業フォルダで読解・図表の切り出しを進めます。重要な図表はノートへプレビューを埋め込み、PDFページと図表番号を添えます。
登録前に画像を研究用の永続フォルダへコピーし、一時キャッシュの削除でプレビューが消えないようにします。
書き出したMarkdownには文書配下の画像を同梱し、数式は独立した`$$`ブロックにします。
保存後にVS Codeなどユーザーの対象Markdownプレビューで図と数式を確認し、原PDFはPDFビューアーで照合します。全ページの読解記録と、科学的な点検・表示確認は別に残します。

ページ番号は表紙・参考文献・付録も含むPDFファイルの1始まりの番号です。印刷ページ番号とは区別します。
取得ツールは`reviewStatus: not_assessed_by_retrieval`を返し、読了を自動判定しません。
空のテキスト、文字化け、抽出エラーのあるページは画像で確認し、必要ならOCRや高解像度で再読します。
文字が取れたページでも、段組み・数式・図表が正しく読めるとは限りません。

PDFのSHA-256が変わったら取得を止めます。新しいPDF版で読解を再開し、古い版と混ぜません。
各リクエストはPDFの一時コピーをOSの一時領域に作り、そのコピーからハッシュ・総ページ数・本文や画像を取得します。
一時コピーは処理後に削除し、Paperpileの原本には書き込みません。

研究用のまとめは全ページ読解を既定とします。要旨や一部ページから作ったメモは、検索候補を選ぶための暫定資料として表示します。
重要な知見には原文のページ・節・図表を付け、ノートを再利用するときにも必要な原文を確認します。

主張を構造化するときは、結論だけでなく、その条件・数値・留保を示す抜粋も紐付けます。抜粋がSourceと完全一致していても、主張を支える範囲まで含むとは限りません。固定文字数で文や語の途中を切らず、必要な方法・結果・図注が離れていれば複数のEvidenceを付けます。独立点検ではMarkdownと登録するClaimの両方を確認します。

## 読解ノートをwikiの更新へつなぐ

論文ごとのMarkdownは、全文を読んだ詳細レビューとして保持します。本文を機械的に転記したMarkdownや抽出テキストとは区別し、方法、結果、成立条件、式の意味、限界、他研究との比較に使える知見を記録します。図表や参考文献を含めた確認範囲も残します。

追加調査では、既存ノートをPDFの版・ハッシュで照合して再利用します。新しい読解結果は、重要な主張の独立点検と論文間の比較を経て、対応するwikiの節へ反映します。ノートの完成だけで、wikiへの統合や依頼全体を完了にしません。解釈を変えない場合も、比較した根拠と変更不要の理由を残します。

原PDF、抽出資料、読解ノート、wikiの役割は[情報の階層](research-knowledge-layers.md)を参照してください。

## 現在の範囲

必要な全文が取得できないときは、研究ワークスペースの`candidates/literature-access.bib`と
`literature-access.md`へ残します。必要な理由、取得状況、無料の代替版、確認日を記録します。
全文プレプリントは対応論文と版を確認して使い、出版版との同等性を未確認のまま断定しません。
bot対策やリンク切れはpaywallと分けて記録します。台帳と研究史の更新は[研究課題の変遷](research-history.md)を参照してください。

PDFは256 MiBまで、本文は1回1〜10ページ、1ページ200,000 UTF-8バイトまで取得します。
ページ画像は長辺2,000ピクセルです。細部が読めない場合は読解済みにせず、元PDFで拡大確認してください。
Popplerの1回の処理は30秒、出力は8 MiBまでです。超過・エラー時には成功した全文として切り詰めず、エラーを返します。
暗号化PDFやスキャン文書の自動OCR、補足資料の自動探索は未実装です。

クラウド上のAIからDrive APIへ直接接続する機能は含みません。今の実装はこのPCのマウントを使います。
PaperpileがDriveへ同期する仕組みと、将来の直接取得に使えるAPIは[Paperpileの説明](https://paperpile.com/h/sync-google-drive/)と
[Google DriveのダウンロードAPI](https://developers.google.com/workspace/drive/api/guides/manage-downloads)を参照してください。
