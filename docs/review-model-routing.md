# 文献レビューでモデルを使い分ける

文献ごとの初稿はLuna maxへ委任でき、結論を左右する根拠・数値・条件は上位モデルが原PDFと照合します。論文間の比較は、その点検結果を受け取った調整役が行います。最後に、ユーザーが読むプレビューで数式と図の表示を確認します。

これは当面の運用方針です。モデル選択はMCPクライアント側で行い、ユーザーが指定した担当モデルと推論設定を守ります。研究エンジンは読解依頼・根拠・ノート・改訂を保存し、特定のLLMには依存しません。

実行時の指示は[研究ハーネス](research-harness.md)の作業別SKILLへまとめています。この文書はモデル選択の判断材料と試行記録として使い、すべての作業に一律の手順を追加するものにはしません。

## 同じPDFはキャッシュを共有し、点検対象を絞る

| 工程 | 担当と完了条件 |
|---|---|
| 既存ノートとPDF版の確認 | 調整役がPDFのSHA-256、総ページ数、現在のノート、未解決事項を確認する。同じ版の本文・ページ画像を再利用する |
| 文献ごとの初稿 | Luna maxを含む担当が全ページを読み、図表・数式・参考文献も確認する。未読・判読不能な資料は明記する |
| 科学的な点検 | 上位モデルが本文の重要な記述と、保存する全Claimの主張・条件・根拠を点検する。数式・単位・比率、測定と推定の区別、図表の条件、例外を原PDFと照合する |
| 保存と論文間の比較 | 調整役が指摘を解消し、改訂番号を確認して保存する。その後、条件を揃えて比較し、研究案を組み立てる |
| 表示の点検 | 保存したノートや出力ファイルを対象プレビューで開き、数式とすべての埋め込み図を確認する |

上位モデルが毎回すべてを最初から読み直す必要はありません。初稿で使った原文とページ画像を共有し、重要な主張とその根拠を照合します。誤読が続く論文や研究判断への影響が大きい論文は、点検を全文へ広げるか、最初から上位モデルへ割り当てます。料金や速度の優劣は、この手順だけでは分かりません。

`full_text_reviewed`は全ページ確認の申告を表します。科学的な点検と表示確認の結果は別に残してください。記録には対象ノートの改訂またはファイルハッシュ、PDFハッシュ、確認者、プレビュー名、確認範囲、未解決事項を含めます。全ページの読了記録があるノートを再利用するときも、以前の点検結果がその版に対応するか確認します。

## Luna maxの試行で分かった範囲を運用に反映する

ダスト輸送の作業では11論文・138ページを読み、21点の図プレビューを作成しました。この全体をモデル比較したわけではありません。

比較試行では、Wang 2016の8ページ論文をLuna maxに既存ノートを見せずに読ませ、別の評価担当が両ノートを原文と照合しました。主要な対照実験と推定値の区別は保持されましたが、粒径分布の分解能と軌跡撮影の分解能を混同する誤りが1件ありました。凝集力と静電力の差も、表の数値から分かる重要な大きさまで説明されていませんでした。既存の上位モデルのノートにも軽微な引用ページのずれがあり、訂正しました。

この結果から、点検では「値が引用されているか」に加えて「どの測定の値か」「比率や桁の差が結論に反映されているか」を確認します。計算が短ければ再計算し、根拠のページを付けます。指摘への対応も原文で確かめ、既存ノートを正解とは決めません。

この比較は1本・1回の試行です。モデル全体の正答率や、二段階処理の費用・所要時間を測ったものではありません。追加の比較では、同じPDFを使った独立した初稿と原文照合に加え、修正時間や実際に得られる使用量を記録します。文量、読了フラグ、スキーマ検証の成功だけでモデルを選ばないでください。

2026年9月15日の追加試行では、6論文・62ページの初稿をLuna maxで並列に作成しました。独立監査では、計算値、測定と推定の区別、条件の抜け、原論文の不整合の扱いに修正が必要でした。本文を直しても、別に保存するClaimに誤りが残る場合がありました。また、引用箇所が原文と一致していても、短く切りすぎて主張の条件を裏付けていない例がありました。

そのため、本文と構造化レコードを別々に点検し、Claim単体を検索しても結果・条件・留保が失われないことを採用条件にします。数値の指数も、抽出テキストの表記をそのまま写さず原PDFで確認します。根拠範囲や参照だけの補正は監査担当が隔離した案として返せますが、調整役が検査し、元の案と変更記録を保管してから保存します。この追加試行も比較ベンチマークではなく、Luna単独での品質保証や費用削減率を示すものではありません。

## 数式と図は、保存後のプレビューで確かめる

本文に書く独立した数式は、開始と終了の`$$`をそれぞれ単独行に置き、ブロックの前後に空行を入れます。数式の区切りに`\(...\)`、`\[...\]`、コード用バッククォートを使いません。文中の`$...$`は対象プレビューが明示的に対応し、実際の表示を確認できた場合に限ります。単純な変数は文章で説明しても構いません。

既存数式の修正では、式ごとに文脈を読み、記号・添字・単位・意味を保ちます。一括正規表現だけで書き換えず、固定されたSource本文やEvidenceの完全一致引用にも手を加えません。

図はMarkdownの画像として埋め込み、PDFページと図表番号を添えます。ファイルの存在確認だけでは表示確認を終えられません。対象プレビューで画像の読み込みと実寸を確認し、実際に表示された図と数式を目視します。持ち運べるMarkdownでは、文書の配下に図のコピーを置き、相対パスで参照します。読み込めない場合は解決後のURL、読み込みエラー、許可されたローカル参照範囲などを調べ、プレビューの安全設定は無効にしません。

今回の図の不具合は、VS Codeの標準Markdownプレビューで再現しました。開いているワークスペースの外にある研究文書から、文書の親ディレクトリを越える画像パスを参照したため、許可範囲から外れていました。文書の配下に画像をまとめて解消し、持ち運び用の出力では文書と画像フォルダを一緒に別の場所へコピーして、移動先のプレビューも確認します。

具体的な割り当て・保存・表示確認は[並列レビューの手順](parallel-review.md)に従います。現在使うノートと出力ファイルを修正し、評価用の未修正ノートや過去の記録は履歴として保持します。過去の評価資料には現行ノートとの違いを明記し、未検証の初稿を正式な知見へ上書きしないでください。
